# 前端用户体验闭环评估报告

> 评估日期：2026-08-18 ｜ 评估视角：前端架构师 + UI 交互设计师 + 终端用户
> 评估方法：对 `frontend/src` 全量代码走查（TanStack Router + react-query + shadcn/ui），逐项核对"用户发起操作 → 系统反馈 → 状态收敛"的闭环完整性，所有结论均有文件与行号佐证。
> 总体印象：**基础设计语言是统一且高质量的**（PageHero/MetricCard/FilterPanel 页面骨架、toast 错误本地化、空状态模式、主题/密度定制），但在**反馈即时性、操作确认一致性、批量入口闭环**三个维度存在系统性缺口。

---

## 一、闭环缺陷清单（按严重度分级）

### P0 —— 用户会"以为自己没点上"或误操作的高危项

| # | 问题 | 位置 | 影响 |
|---|------|------|------|
| P0-1 | **互动"确认发送"按钮无 loading、无确认、可重复点击**。互动是会真实发送到抖音的写操作（消耗账号配额、有风控后果），但 `confirm` 按钮点击后没有任何进行态，网络慢时用户极可能连点，造成重复发送风险 | `douyin-interactions.tsx:401-408`、`TaskInteractionsPanel.tsx:166-173` | 真实资金/风控后果，最高优先级 |
| P0-2 | **取消任务无二次确认**。任务详情页"取消任务"是 destructive 按钮，点击即触发 `cancelMutation`，无 Dialog、无 confirm。长时间运行的任务一次误点即终止 | `douyin_.$taskId.tsx:170-181` | 数据采集中断成本不可逆 |
| P0-3 | **互动"取消"无确认、无 toast、无 loading**——三重缺失：点击后立即请求，成功后仅靠轮询静默回显 | `douyin-interactions.tsx:421-429`、`TaskInteractionsPanel.tsx:193-201` | 与 P0-2 同类的破坏性操作裸奔 |
| P0-4 | **二维码登录无过期/超时 UI**。`TaskQrCode` 每 15 秒轮询新二维码，但若用户一直不扫码，页面无限停在"等待扫码"状态，没有"二维码已过期，点击刷新"或"已超过 N 分钟未扫码"的提示，用户无法分辨"还在等"还是"已卡死" | `douyin_.$taskId.tsx:379-447`（轮询在 415 行） | 新用户首次使用的关键路径 |

### P1 —— 反馈缺失（静默成功）与批量闭环断点

| # | 问题 | 位置 | 建议 |
|---|------|------|------|
| P1-1 | **启停类操作全部无成功 toast**：赛道启停、关键词启停、账号启停三处 `toggle` 的 `onSuccess` 都只 `invalidate`，靠 3-10 秒轮询回显。轮询间隙用户得不到任何确认 | `douyin-tracks.tsx:125-135`、`douyin-keywords.tsx:169-177`、`douyin-accounts.tsx:154-162` | 统一在 `onSuccess` 加 `showSuccessToast("已启用/已停用")` |
| P1-2 | **批量建任务后"不知道去哪"**：关键词批量建任务（`BatchTaskDialog`）与赛道工作区建任务（`TrackWorkspaceDialog`）成功后仅 toast + 关闭弹窗，不跳转新任务、甚至**不失效 `douyin-tasks` 查询**（用户此时切到任务列表看到的还是旧数据）。对比：单任务创建（`CreateTaskDialog.tsx:156`）和单视频追爬（`AwemeActions.tsx:112-122`）都会跳转任务详情——三个入口三种行为 | `douyin-keywords.tsx:606-848`、`douyin-tracks.tsx:630-666` | 成功后失效 `douyin-tasks` + 提供"查看任务"的 toast action 或直接跳转 |
| P1-3 | **字幕正文无查看入口（功能断裂）**：字幕 `full_text` 的唯一渲染处在 `MediaPipelinePanel.tsx:291-302`，但该组件**全项目未被任何路由引用（死代码）**；激活的 `UnifiedWorksPanel` 字幕列只显示状态/进度/错误。用户生成了字幕却**在前端看不到字幕内容**，只能导出文件或播放视频看字幕轨 | `UnifiedWorksPanel.tsx:656-669` 对比 `MediaPipelinePanel.tsx:291-302` | 在字幕列加"查看字幕"弹窗；顺带清理或重新挂载 MediaPipelinePanel（另有 `TaskResults.tsx` 同为未引用遗留组件） |
| P1-4 | **媒体单条操作图标无 loading**：单条"重试/重新翻译/下载"图标按钮未接 mutation 的 pending 态（批量入口有 `isPending`，单条没接线），慢网络下用户会连点 | `UnifiedWorksPanel.tsx:567-600`、`douyin-library.tsx:671-702` | 给单条 mutation 增加行级 pending 禁用 |
| P1-5 | **互动"重试"按钮无 loading**（needs_review 时有 confirm，但按钮本身无进行态） | `douyin-interactions.tsx:409-420`、`TaskInteractionsPanel.tsx:174-192` | 同 P1-4 |

### P2 —— 一致性债务与结构性问题

| # | 问题 | 位置 | 建议 |
|---|------|------|------|
| P2-1 | **确认机制双轨制**：原生 `window.confirm`（10 处：删账号、删账号池、批量删关键词、批量重试互动、本地转云端、移动关键词等）与样式化 shadcn Dialog（删赛道、删关键词、恢复任务、迁移媒体等）混用。原生 confirm 样式突兀、无法展示详细后果说明，与整体设计语言割裂 | 详见第五节统计 | 收敛为统一的 `ConfirmDialog` 组件；破坏性越强、说明越多的操作越应该用 Dialog |
| P2-2 | **任务无法删除**：SDK 层即无 `deleteTask`，前端无任何删除入口，任务只能取消。长期运行后任务列表只能无限累积 | `sdk.gen.ts:253-274` | 需要后端先补删除能力（涉及作品/评论级联策略），属产品决策而非纯前端问题 |
| P2-3 | **账号扫码登录全程无二维码**：账号"登录"操作弹远程浏览器窗口（`window.open(viewer_url)`），二维码只出现在真实浏览器画面里。如果弹窗被拦截或用户没注意到新窗口，流程就断了 | `douyin-accounts.tsx:108-134` | 弹窗前给明确引导文案；检测弹窗拦截（`window.open` 返回 null）并降级为页面内 noVNC 链接 |
| P2-4 | **`/items` 路由存在但不在侧边栏**：模板遗留页面只能 URL 直达，对终端用户是死入口，对系统是维护噪音 | `routeTree.gen.ts`、`AppSidebar.tsx:30-81` | 业务项目应删除 items 切片（前后端一起），或明确保留理由 |
| P2-5 | **页面级加载态不统一**：admin/items 用 `<Suspense>` + 骨架屏，业务页面多为文字占位（"正在加载任务…"），视觉规格不一致 | `PendingUsers.tsx` 对比 `douyin.tsx:254-257` | 统一 Skeleton 规格 |
| P2-6 | **标签页只读无轮询但无说明**：标签是自动抽取的只读数据，页面无新建/删除入口（设计正确），但同步后列表不自动刷新（无 `refetchInterval`），用户点完"同步历史标签"要手动刷新才看到新标签 | `douyin-tags.tsx`（轮询缺失） | 同步成功后 `invalidate` 标签查询即可（当前仅 toast） |

## 三、按用户角色的断点场景还原

### 场景 1：运营新人发出第一条评论回复（当前会发生什么）

进入评论管理 → 找到目标评论 → 点"回复" → 两段式弹窗（选账号→写内容→发送前检查→确认发送）✅ 这段很好 → 发送后到互动任务页 → 看到 `needs_review` → 点"确认发送"——**按钮没有任何反应**（P0-1）→ 不确定点没点上，再点一次 → 列表 2 秒轮询后状态才变 → 用户无法确认是点了两次还是一次。

### 场景 2：批量建 20 个关键词任务（当前会发生什么）

关键词页勾选 20 条 → 批量建任务 → 配置 → 提交 → toast"成功" → **停留在关键词页**（P1-2）→ 用户想确认任务起来了没有，手动切到"抖音任务"——**列表还是旧数据**（查询未失效，要等 3 秒轮询）→ 用户困惑"任务到底建了没有"。

### 场景 3：想看某个视频的字幕（当前做不到）

任务详情 → 作品面板 → 字幕列显示"已完成" → **没有任何按钮能看字幕内容**（P1-3）→ 用户只能点导出字幕文件下载到本地用记事本打开。字幕从"数据资产"变成了"只能导出不能读"的半成品。

### 场景 4：扫码登录卡在等待页（当前会发生什么）

创建任务选扫码登录 → 二维码出现 → 用户去拿手机 → 回来二维码已换过两轮（15 秒/轮）→ 扫了旧码失败 → 页面**没有任何"二维码已刷新，请重新扫"的提示**（P0-4）→ 用户反复扫旧码，直到任务超时失败。

## 四、优化路线图（按投入产出排序）

### 第一梯队：一行到几行代码，收益立竿见影
1. **所有启停 toggle 补成功 toast**（P1-1，3 处，每处 2 行）
2. **批量建任务成功后失效 `douyin-tasks` 查询 + toast 带"查看任务"跳转**（P1-2，2 处）
3. **互动三操作（确认发送/重试/取消）接 `isPending` 禁用**（P0-1/P1-5/P0-3 的 loading 部分，变量已存在只是没接线）
4. **同步标签后 invalidate 查询**（P2-6）
5. **单条媒体操作图标接行级 pending**（P1-4）

### 第二梯队：小组件级改造
6. **统一 `ConfirmDialog` 组件替换 10 处 `window.confirm`**（P2-1），并给取消任务、取消互动补上确认（P0-2/P0-3 的确认部分）
7. **字幕查看弹窗**：字幕列加按钮，复用 `full_text` 渲染逻辑（从死代码 `MediaPipelinePanel` 迁移过来），顺带删除两个未挂载遗留组件（P1-3）
8. **二维码过期提示**：`TaskQrCode` 增加"已等待 N 秒/二维码每分钟刷新，请扫最新码"的预期管理文案与手动刷新按钮（P0-4）

### 第三梯队：需要产品决策
9. **任务删除能力**（P2-2）：需要后端定义级联策略（作品/评论/媒体是否同删），再进前端
10. **账号登录弹窗拦截检测与页面内降级**（P2-3）
11. **清理 items 模板遗留切片**（P2-4，前后端一起）

## 五、确认机制现状统计（一致性债务的证据）

| 确认方式 | 数量 | 用在哪 |
|----------|------|--------|
| 样式化 Dialog（符合设计语言） | 6 处 | 删赛道、删关键词、移除关键词、恢复任务、迁移媒体、批量媒体处理 |
| 原生 `window.confirm`（突兀） | 10 处 | 删账号、删账号池、批量删关键词、批量重试互动、单条重试互动、本地转云端、移动关键词×2 等 |
| **无任何确认**（危险） | 3 处 | 取消任务、取消互动、互动确认发送 |

一个系统里同一种"破坏性操作"出现三种防护等级，且**防护等级与真实风险成反比**（发抖音评论无防护，删本地关键词反而有正式 Dialog）——这是最需要向团队传达的结构性结论。
