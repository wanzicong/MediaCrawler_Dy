项目业务与技术架构分析

📦 分析对象：MediaCrawler_Dy（抖音内容采集与运营中台） 📅 分析日期：2026-08-18
🔍 分析方式：三路并行代码探索（业务域与数据模型 / 任务编排与技术分层 / 平台集成与部署链路）+ 设计文档交叉验证

一、项目定位

这是一个抖音内容采集与运营中台：以 full-stack-fastapi-template 0.10.0 为骨架，把 MediaCrawler 的抖音抓取能力重构成一个多租户、任务化、可断点恢复的数据平台。它解决四件事：

  1. 采集：关键词搜索 / 指定作品 / 创作者作品 / 账号点赞 / 账号收藏，五类内容进库；
  2. 组织：用"赛道"做一级业务归属，关键词、任务、内容全部按赛道归档；
  3. 加工：视频下载 + 远程 Whisper 字幕转录，本地/MinIO 双存储；
  4. 运营：人工确认制的评论/私信写回（互动），并对外提供 Web、REST、MCP 三种等价入口。

2.2 数据模型与归属链（14 张表）

核心洞察：作品、评论、媒体都不直接挂赛道，而是挂在任务上，经由任务传导归属。

user ─┬─ DouyinTrack (每用户必有 1 个 is_default，部分唯一索引保证)
      │     ├─< DouyinKeyword  (track_id 非空, 复合FK NO ACTION)
      │     └─< CrawlTask      (track_id 非空, 复合FK NO ACTION)
      ├─ DouyinAccount ─< DouyinAccountPoolMember >─ DouyinAccountPool
      ├─ DouyinTag (用户级全局，跨赛道)
      └─ DouyinInteraction (Fernet 加密正文 + 事件审计表)

CrawlTask ─┬─< DouyinAweme      (task_id, CASCADE) ─< DouyinAwemeTag >─ DouyinTag
           ├─< DouyinComment    (task_id, CASCADE)
           ├─< DouyinUserAction (点赞/收藏私有流的行为记录, account_hash 脱敏)
           ├─< DouyinMediaAsset (task_id, CASCADE) ─1:1─ DouyinSubtitle
           └─< CrawlTaskShard   (多账号分片执行)

归属链：Aweme/Comment/Media → task_id → CrawlTask.track_id → DouyinTrack

关键模型文件：backend/app/domain/douyin/tasks/models.py（任务骨架 + 全部状态枚举）、backend/app/domain/douyin/tracks/models.py、backend/app/domain/douyin/accounts/models.py。

隐私设计贯穿全库：creator_hash/account_hash 是 HMAC-SHA256 脱敏指纹，昵称打码（首字+***+尾字），互动正文 Fernet 加密存储，Cookie/原始 uid 永不落库——见 backend/app/integrations/douyin/privacy.py。

2.3 赛道（track）：一级归属维度

赛道是整个业务组织的枢纽，规则由 backend/app/application/douyin/tracks/bindings.py 和 backend/app/application/douyin/tracks/service.py 实现：

  • 强制归属：关键词和任务必须且只能归属一个赛道；未传 track_id 时自动落入"默认赛道"（对用户行 SELECT FOR UPDATE 消除首请求竞态）。
  • 默认赛道保护：不可删除、停用、重命名；被停用会自动复活。
  • 删除不丢数据：复合外键是 NO ACTION，删除赛道前由应用层把其下关键词和任务逐一迁回默认赛道（_rehome_track_records），作品评论媒体原样保留。
  • 派生继承：评论重爬、作者作品跟进等子任务继承源任务赛道；跨用户场景（超管操作他人数据）则回落到新所有者的默认赛道，防止跨租户归属。
  • 关键词移动赛道只影响将来：历史任务和内容保留原赛道，报表不被追溯改写。

2.4 任务系统：6 种爬取类型

类型业务语义目标字段可分片
search关键词搜索流（时间过滤+翻页+评论）keywords✅ 按词分片
detail指定作品详情（支持短链）video_ids✅ 按作品分片
creator指定作者全部作品（游标翻页）creator_ids✅ 按作者分片
creator_from_aweme从作品反查作者再抓其作品（作者跟进）video_ids✅
liked账号点赞流（私有）无（self）❌ 单账号
collected账号收藏流（私有）无（self）❌ 单账号

分发入口在 backend/app/application/douyin/tasks/crawler.py 的 _dispatch。任务间存在派生关系：资源库中任一作品可派生"评论重爬"（detail）和"作者作品跟进"（creator_from_aweme）两类独立子任务，源任务结果不受影响。

进行中的业务演进：根据 docs/灵感私藏模块设计.md，liked/collected 两类私有同步将从普通任务体系剥离为独立的"灵感私藏"模块（track_id 改可空、查询层隔离、专属路由 /douyin/vault/* 和前端页签），成为独立业务线——这是当前分支正在推进的方向。

2.5 账号与浏览器资源池

账号是"登录态 + 浏览器槽位 + 风控配额"的三合一资源（backend/app/application/douyin/accounts/service.py）：

  • 浏览器绑定二选一：local（本机 Chrome 独立 profile，调试端口按账号 ID 派生）或 remote（绑定 Docker 远程槽位，槽位 1:1 独占校验）。
  • 登录态不落库：扫码登录靠浏览器 profile 持久化，库里只存 identity_hash（HMAC 指纹，非空即"已登录"），并做同身份去重。
  • 账号池调度：least_loaded / round_robin / weighted_round_robin 三种策略；reserve_account 用行锁发租约（active_leases），受 concurrency_limit、daily_task_limit、cooldown_until 约束；连续失败 3 次自动 unhealthy。
  • 风控节奏：任务级三档请求间隔（fast 1-2s / steady 3-6s / ultra_steady 6-12s，每次随机），且会被账号的 min_request_interval_seconds 抬高——账号级风控下限优先。

2.6 内容消费与运营

  • 资源库 library：跨任务的作品聚合视图（作品+评论数+媒体+字幕+标签），支持赛道/作者/标签/下载态/字幕态多维筛选与排序，是派生子任务和库级 MinIO 迁移的入口。
  • 评论库：跨任务多维检索（内容、赛道、作品、作者、来源关键词、顶级/回复、有无图、点赞区间、时间区间）+ 按作品分组导出 txt。
  • 标签：作品入库时用正则从描述中提取 #话题#，用户级全局 upsert——赛道之外的第二套横向分类维度。
  • 互动（写回）：全系统最谨慎的模块。发评论/回评论/私信必须人工确认后执行；预检做日配额、24h 重复内容去重、编码损坏检测；执行按账号串行 + 截图留证 + 事件审计；结果不确定时（重启/超时）进入 needs_review，必须人工确认"未发送"才能重试，从机制上杜绝重复发布。幂等键 = sha256(所有者|账号|类型|作品|目标|内容哈希|日期)。

这套分层不是靠文档约束，而是靠 backend/tests/architecture/ 契约测试机器强制：

  • AST 依赖方向检查：api 禁止 import sqlmodel/playwright/minio，application 禁止 import fastapi，API 层连 session.add/commit 都禁止调用（事务边界强制下沉）；
  • 公共契约哈希冻结：OpenAPI（76 paths/112 schemas）、SQLModel metadata（21 表）、32 个 MCP 工具的 schema、30 条抖音路由注册顺序，任何变更都会红；
  • 兼容门面身份测试：旧路径（app.services/*、app.douyin/*、app.core/*）与 canonical 路径必须 is 同一模块对象，防止迁移期单例分叉。

3.2 运行时组件：4 个后台 Manager

backend/app/main.py 的 lifespan 只启停两个 Manager，但它们级联拉起全部后台能力：

FastAPI lifespan
 ├─ task_manager.startup()      标记残留活动任务→interrupted
 │   ├─ 重置账号租约
 │   ├─ media_manager.startup()        媒体下载+字幕流水线
 │   └─ media_migration_manager.startup() 恢复未完成的MinIO迁移
 └─ interaction_manager.startup()  残留running互动→needs_review，重排queued
Manager职责并发控制
DouyinTaskManager任务生命周期、分片、恢复全局信号量 DOUYIN_MAX_ACTIVE_TASKS（只管匿名临时 CDP 任务）；托管账号任务走账号租约
MediaPipelineManager视频下载 + 远程字幕FairLimiter 跨任务公平限流（按 task_id 轮转）
MediaMigrationManager本地→MinIO 校验迁移信号量 MEDIA_MIGRATION_CONCURRENCY
DouyinInteractionManager互动写回执行每账号一把 asyncio.Lock 串行

backend/app/framework/concurrency/fair_limiter.py 的 FairLimiter 是最精炼的设计：总并发有上限，同时在不同 key（任务）间轮转发放槽位——大任务的一百个视频不会堵死后提交的小任务。

3.3 任务执行主链路（POST /tasks → 落库）

① HTTP 入站   douyin_tasks.py 鉴权(JWT)+归属(scope: 超管看全部/普通用户看自己)
② 命令适配    api_service.create_task → task_manager.create
③ 编排落库    校验上限 → 填默认 browser_mode/media_storage → 账号池选号
             → DouyinStorage.create_task(status=queued, checkpoint.phase=crawl)
             → asyncio.create_task 后台跑，立即返回 202
④ 浏览器与登录 CDPBrowserSession attach(CDP-only，无 launch 回退)
             → DouyinClient.create: 从活浏览器取 Cookie/UA/msToken
             → 扫码(on_qrcode→waiting_login) 或 Cookie 注入 → running
⑤ 按类型爬取  _dispatch → search/detail/creator/personal_feed
             每轮迭代: 先 _save_position 写断点 → 按间隔档 sleep → 发签名请求
⑥ 读数据      httpx 直发抖音 Web API（a_bogus 签名 = execjs→Node 执行 douyin.js）
             ※ 浏览器只做"身份提供者"，读数据不走页面拦截
⑦ 脱敏落库    privacy.map_aweme/map_comment → PG insert on_conflict upsert
             (幂等，断点重抓不重复) → 同步提取标签 → 刷新任务计数
⑧ 媒体阶段    immediate: 作品入库即入队 / batch: 爬完统一入队
             status=processing_media → 下载(边下边算SHA-256) → FFmpeg抽音频
             → 远程 Whisper 转录 → DouyinSubtitle
⑨ 终态        succeeded / failed / cancelled；finally 释放账号租约
⑩ 崩溃恢复    重启标 interrupted → resume 读 checkpoint 续爬
             (关键词序号/页码/游标/待补评论/媒体队列全在 checkpoint_json)

3.4 断点恢复：最有工程含量的部分

  • 断点即数据：checkpoint_json = {version, phase, crawl_type, position}，每轮循环先写断点再发请求；Cookie/Token/原始 uid 刻意不进断点。
  • 每种类型有专属断点结构：search 存 target_index + page + stage + pending_aweme_ids（中断在评论阶段会先补评论再推进）；creator 存 cursor/has_more；detail 存 completed_indexes。
  • 幂等兜底：作品/评论/行为全部 (task_id, 业务键) 唯一约束 + on_conflict_do_update，重抓天然不重复。
  • 阶段化恢复：phase=crawl 续爬取、phase=media 只补媒体（重新扫描全部作品入队，已下载的幂等跳过）、phase=completed 允许单项失败重试。
  • 重启语义保守：服务启动只标记 interrupted，未经用户确认不自动碰浏览器，由用户通过 Web/REST/MCP 显式 resume。

3.5 数据访问与并发模式

不走 Repository 抽象，而是两种务实形态：

  • 请求级：FastAPI 注入 SessionDep，事务边界 = 单个 application service 函数；
  • 后台 Manager：每个 DB 操作是 _*_sync 同步方法（自带 with Session(engine) + commit），用 asyncio.to_thread 卸载出事件循环——每步独立提交，正好匹配断点续爬"崩溃不丢已存数据"的需求。

并发安全三件宝：with_for_update() 行锁（账号租约、迁移切换）、on_conflict upsert（幂等写入）、asyncio 原语（信号量/Lock/FairLimiter）。

3.7 媒体流水线（下载→转录→迁移→播放）

下载: .staging 暂存 → 流式边下边算 SHA-256 → 校验 MIME/大小 → .part 原子落盘
      → local(MEDIA_OUTPUT_DIR) 或 minio(bucket=douyin-media, key=douyin/{task}/{comp}/source.mp4)
转录: materialize(minio 先拉回临时目录) → FFmpeg 抽 16kHz 单声道 MP3
      → POST 远程 Whisper /v1/audio/transcriptions (非回环必须 HTTPS，无本地回退)
迁移: 本地指纹(size+sha256+mtime) → 上传 → 全量回读校验 SHA-256(ETag 不算数)
      → 行锁切库 → 删本地；失败保本地、cleanup_pending 可续、重启自动恢复
播放: <video> 不能带 Header → POST preview-session 换 HttpOnly Cookie(HMAC票据,300s)
      → GET preview 验票 → RFC 7233 Range 解析 → 206 流式(本地分块/MinIO offset读)

3.8 MCP 网关与前端

  • MCP（backend/app/mcp_server/）：FastMCP 实现的 API 网关，AuthenticatedApiClient 先登录拿 JWT 再把 32 个工具全部代理到 REST——Web、REST、Agent 三者共享同一套权限、状态机和数据，MCP 重启不影响运行中任务。streamable-http 绑 127.0.0.1:8766，开 DNS rebinding 防护。
  • 前端：React 19 + Vite + TanStack Router（文件式路由）+ TanStack Query（无 Redux，服务端状态全走 react-query）+ shadcn/ui。API client 由 @hey-api/openapi-ts 从 openapi.json 生成 12 个 Service 类——改后端接口后重新生成即可，前后端类型永远一致。

四、架构亮点与观察

设计得最扎实的四处

  1. 断点恢复体系——断点即数据、幂等 upsert 兜底、阶段化恢复、重启语义保守，构成了完整的"崩溃友好"闭环；
  2. 隐私边界——从集成层脱敏（源头）到异常链掐断（日志）到 Fernet 加密（存储），Cookie/uid 的全链路隔离是被架构测试和审查规则双重强制的；
  3. 公平限流——FairLimiter 用很小的代码量解决了"大任务饿死小任务"的调度公平问题；
  4. 契约测试门禁——OpenAPI/表结构/MCP 工具/依赖方向全部哈希冻结，让大规模分层重构（该项目刚经历过）不破坏对外行为。

值得注意的演进点

  • 灵感私藏（vault）模块正在把 liked/collected 从赛道体系剥离，会带来 crawl_task.track_id 可空化的迁移——这是数据模型层面的一次重要松动；
  • compose.storage.yml 与 compose.yml 内容重复（MinIO 定义已并入主文件，属遗留技术债）；
