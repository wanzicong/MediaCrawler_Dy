## 1. Summary

本文档把「灵感采集台」（抖音内容运营工作台，React 19 + TanStack Router/Query + shadcn/ui 前端，FastAPI 后端）的设计产出固化为一份工程可执行的交付契约：以单文件交互原型为视觉/交互唯一权威源，以既有产品 PRD 的 FR-编号为功能唯一权威源，本规范负责两者到工程代码的**逐文件映射**（路由文件、组件路径、数据接入、轮询策略、异常态矩阵、Given/When/Then 验收标准），并定义后续迭代的维护协议。成功标准：任何 coding agent 不追问人类即可完成任一页面的开发或改版，且产出可通过本文档的验收标准与仓库质量门禁。

## 2. Background & Problem

**现状**：产品已上线，前端 21 个路由文件、17 个抖音领域组件、9 个通用组件全部实现完毕。项目文档链完整但分散为四份：交互原型（视觉）、产品 PRD（功能）、逆向能力文档（文案）、体验评估报告（问题清单）。一份给"人"读的文档链，不等于给"agent"读的工程契约。

**当前 workaround**：迭代时把需求口述给工程师或 agent，由其自行在四份文档和代码之间推断落点——每次交接都在重复消耗对齐成本，且推断结果无验收标准兜底，容易产生视觉漂移（间距、色值、状态缺失）和文案漂移。

**为什么是现在**：项目进入「IA 优化方案三批次」迭代期（见 §8.3），后续改动将大量交给 coding agent 执行；没有一份机器友好的映射契约，agent 每次都要重新理解全仓库，产出质量不可控。

**不解决什么**：本文档不定义后端架构与 API 契约（后端 OpenAPI 是权威，前端 client 由 `openapi-ts` 生成）；不定义商业目标与优先级论证（见产品 PRD §1）；不替代逐字文案基线（见逆向能力文档）。

## 3. Personas / 文档消费者

本文档的主要消费者不是终端用户，而是**开发者与开发代理**，终端用户 persona 摘编自产品 PRD §2：

**Primary — Coding Agent（Cursor / Claude Code / 千问办公等）**

```
身份：被指派实现或改版某个页面的 AI 编程代理
情境：收到一句话任务（如"把关键词页的获取状态列升级为采集概览列"）
JTBD：当收到模糊指派时，Agent 想·按唯一权威源直接定位到要改的文件与验收标准，从而·不追问人类完成符合设计基线的实现
痛点：文档链分散、无组件级映射、无机器可验证的验收标准
```

**Secondary — 人类维护者（本仓库的开发者）**

```
身份：负责评审 agent 产出、维护文档链的工程师
JTBD：当产品/设计变更时，想·按固定顺序更新文档链并留下修订记录，从而·保证三份基线文档不漂移
```

**终端用户（摘编）**：内容运营（全部业务页）、超级管理员（额外见用户管理）、访客（仅认证四页）。权限细则见产品 PRD §2.1。

**本文档不为谁做**：不为 PM 的优先级论证服务，不为无设计基线的全新页面服务（新页面必须先产出原型，见 §8.5）。

## 4. Goals & Success Metrics

**产品目标**（outcome 摘自产品 PRD §1.3）：采集可追踪、资产可沉淀、互动可管控、环境可隔离。

**本文档自身的工程度量**：

| 指标 | 度量什么 | 目标值 | 时间窗 |
| --- | --- | --- | --- |
| 页面覆盖率 | 逐页规格（§6.5）覆盖全部路由文件 | 21/21（含 2 页设计源缺失标记） | 本版 |
| 零追问交付 | agent 实现任一页面所需的人类澄清次数 | ≤1 次/页面 | 每次迭代 |
| 验收可执行 | 每页 Given/When/Then 验收条目 | ≥2 条/页，全部可人工或 Playwright 验证 | 本版 |
| 三态完整 | 空态/加载态/错误态在所有列表页的实现率 | 100%（以 §6.6 矩阵核查） | 每次验收 |
| 文档同步率 | 设计/需求变更后三份基线文档同步更新的变更占比 | 100%（按 §8.5 协议执行） | 长期 |

**Anti-metrics（不优化什么）**：不为减少文档行数而牺牲逐字文案引用（文案漂移是红线）；不为 agent 方便而允许绕过质量门禁（lint/build/架构测试不可跳过）。

**关键假设**：原型与线上实现保持 1:1 对齐这一前提持续成立。若二者漂移超过一个迭代周期，本文档的映射表失效——§8.5 的维护协议即为此假设的保险机制。

## 5. Value Proposition

**对 Coding Agent**：终于可以按「render 函数 → 路由文件 → 组件 → client SDK 函数」的确定性路径直接落码，而不必通读全仓库后猜测设计意图——每个原型 class 都有对应工程组件路径（§6.3），每页都有验收标准（§6.5）。

**对人类维护者**：把"交接知识"从口述沉淀为契约。评审 agent 产出时逐条核对验收标准即可，评审成本从"重看整个页面"降为"核对差异点"。

**差异化**：传统 PRD 到代码之间隔着"设计稿翻译"损耗；本项目因原型 token 复刻工程 CSS 变量、render 函数与路由文件一一对应，本规范把这条翻译路径显式化为表格，使损耗降为零。

## 6. Solution & 工程规范（核心章节）

### 6.1 权威源与引用关系

```text
视觉/交互  ← 唯一权威源：docs/灵感采集台交互原型.html
功能/规则  ← 唯一权威源：docs/灵感采集台产品需求文档PRD.md（FR- 编号）
逐字文案   ← 唯一权威源：docs/前端逆向产品能力文档.md
API 契约   ← 唯一权威源：后端 OpenAPI → frontend/src/client（生成物，禁止手改）
工程落点   ← 本规范 §6.2–6.6（路由文件、组件路径、数据接入、验收标准）
```

冲突裁决规则：文案冲突以逆向能力文档为准；功能冲突以产品 PRD 为准；两者都未定义的视觉细节以原型为准；原型与实现冲突时，以本规范 §6.5 各页「设计源漂移」字段标注的决策为准。

### 6.3 设计 Token 与组件映射规范

原型的 CSS 变量**复刻自** `frontend/src/index.css`（默认 violet preset，另有 ocean/graphite 两套 `[data-preset]`、暗色 `html.dark`、紧凑 `[data-density="compact"]`）。规则：

1. **禁止在页面代码中写死色值/间距**——一律使用工程同名 CSS 变量或 Tailwind 语义 token；原型里的 `oklch(...)` 字面量只存在于 `index.css`。
2. **禁止复制原型 CSS 到工程**——原型样式仅作视觉参照，工程实现走组件 + Tailwind。

### 6.4 数据层规范

1. **API 调用只走生成 client**：`frontend/src/client/`（`sdk.gen.ts` / `types.gen.ts` / `schemas.gen.ts` / `core/`）。后端 API 变更后先 `npm run generate-client` 再写前端代码；**禁止手改生成物**、禁止在 client 之外手写 axios/fetch 调用业务接口。
2. **服务端状态一律 `@tanstack/react-query`**：key 命名遵循现有各页 query 约定；翻页用 `placeholderData` 保留上一页数据；写操作成功后精确失效对应 query（历史教训：批量建任务入口曾漏失效任务列表查询，属 P1 级闭环缺陷，见体验评估 §1.1）。
3. **轮询间隔**（`refetchInterval`，权威表＝产品 PRD §7.2，摘录）：

| 位置 | 间隔 | 位置 | 间隔 |
| --- | --- | --- | --- |
| 互动实时监控详情 | 1s | 互动列表/面板 | 2s（进行中）/ 5s |
| 任务详情/分片（活跃） | 2s | 工作台任务 | 5s |
| 统一工作区 | 2s（活跃）/ 5s | 资源库 / 账号池 / 浏览器监控 | 5s |
| 任务列表 | 3s | 关键词列表/概览 | 5s / 10s |
| 作品评论弹窗（开+活跃） | 3s | 赛道列表/详情 | 10s |
| 互动配额 | 5s | 评论管理 | 不轮询（手动刷新） |

4. **错误处理**：query 错误走 `QueryErrorState`（重试按钮）；后端英文错误码经中文化映射表转 Toast（12 条映射 + 网络错误兜底，清单在逆向能力文档）；403/404 资源级提示「{资源}不存在，或当前账号无权访问」。
5. **行级操作 pending**：用 `mutation.variables` 级禁用，仅禁当前行按钮。
6. **安全红线（前端侧）**：受保护媒体/导出/截图请求携带 `Authorization: Bearer {token}`；视频预览先建短时 preview-session；临时凭据仅内存、不落库不落日志（UI 明示）；不得在任何页面/日志/Toast 中输出 Cookie、Token、原始账号 ID。

### 6.5 逐页开发规格与验收标准

> 每页格式：**落点文件 → 功能基线（FR 编号）→ 验收标准（Given/When/Then）→ 异常态**。功能与文案细节以 FR 编号指向产品 PRD，本文不重复抄录；agent 实现前必须点开对应 FR 条目阅读全文。

#### P0-01 工作台 `/`

- **落点**：`routes/_layout/index.tsx`
- **基线**：FR-DASH-01；原型 `renderDashboard()`
- **验收**：
  - Given 工作台已登录，When 存在 failed/interrupted/waiting_login 任务，Then 异常横幅出现且计数与接口一致；Given 需关注数为 0，Then 横幅不渲染
  - Given 任务 5 秒轮询进行中，When 用户滚动页面或点击任务卡，Then 轮询不中断、跳转任务详情正常
  - Given 账号或任务接口任一失败，Then 仅对应数据块渲染错误态，页面其余部分正常
- **异常态**：任务空态（含「前往任务中心」跳转）；账号/任务双错误块

#### P0-02 赛道管理 `/douyin-tracks` 与赛道详情

- **落点**：`douyin-tracks.tsx` / `douyin-tracks_.$trackId.tsx`
- **基线**：FR-TRACK-01~04；原型 `renderTracks()` / `renderTrackDetail()`
- **验收**：
  - Given 默认赛道，When 打开行菜单，Then「停用」「删除」为禁用态且 title 为对应文案（「默认赛道必须启用」「默认赛道不可删除」）
  - Given 删除非默认赛道，When 确认，Then 二次确认文案含「赛道删除后无法恢复」，成功后原赛道关键词归属默认赛道（列表可验证）
  - Given 赛道停用，Then「运营这个赛道」按钮禁用且 title 提示「请先启用赛道再启动采集」
  - Given URL 带 `?run={trackId}`，Then 直接打开该赛道运营工作区
- **异常态**：空赛道空态文案；工作区三类超限警示（每词独立 ≤20 / 部分选择 ≤200 / 停用词不参与）

#### P0-03 抖音任务 `/douyin` 与任务详情

- **落点**：`douyin.tsx` / `douyin_.$taskId.tsx`
- **基线**：FR-TASK-01~05；原型 `renderTasks()` / `renderTaskDetail()`

## 7. Constraints & Risks

**技术约束**：
- 前端质量门禁：`npm run lint`（biome）+ `npm run build`（tsc + vite）+ `bunx playwright test`（涉及时）
- 后端 API 变更必须先过仓库根 `AGENTS.md` 的全部门禁（ruff/mypy/pytest/alembic check + 四哈希契约测试），前端再 `npm run generate-client`——**OpenAPI 哈希契约测试意味着任何后端接口改动都会被架构测试捕获，agent 不得绕过**
- 模块依赖方向固定 `api -> business -> douyin-client -> browser -> bootstrap`，前端任务不涉及后端时禁止触碰 modules/

**设计约束**：明暗三模式（浅/深/跟随系统）× 三主题 × 两密度全组合下页面不可破版；色值只走 CSS 变量；图标只用 lucide-react。

**数据与隐私红线**（源自 AGENTS.md「必须遵守」，前端侧执行见 §6.4 第 6 条）：Cookie/Token/原始账号 ID 不入库不入日志不入 API 响应；创作者/评论用户信息脱敏后落库；临时凭据内存级使用。

**关键风险表**：

| 风险 | 可能性 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 原型与实现漂移（本文档映射表失效） | 中 | 高 | §8.5 维护协议：改原型必须同步本规范；每版本记录基线提交哈希 |
| agent 绕过 client 手写请求 / 手改生成物 | 中 | 高 | code review 核对 §6.4；生成物 diff 应为空 |
| 设计源缺失页被 agent 擅自重设计 | 中 | 中 | §6.5 冻结区标注 + review 清单含此项 |
| 已知问题 #1（假服务状态）误导运营 | 高 | 中 | §8.3 批次 0 优先修复（接真实健康检查或下线徽章） |
| 文案漂移（agent 自造文案） | 高 | 中 | 逐字文案以逆向能力文档为准；review 时 diff 文案行 |
| 密度/暗色/主题组合破版 | 中 | 中 | §8.4 验收含三模式 × 三主题 × 两密度走查 |

**已识别未修复的设计问题**：产品 PRD §10.1 共 16 项（1 项功能缺陷×2、技术债×1、本地化×4、文案一致×4、体验×1、规模×1、安全依赖×1），其中高优先级项纳入 §8.3 批次 0。

## 8. Release Approach 与维护协议

### 8.1 推荐交付顺序

先修基线再迭代：批次 0（对齐与修复）→ IA 优化三批次（体验评估文档已给出依赖关系与工作量）。理由：已知问题中的文案口径不统一会污染后续所有改版的验收基准，必须先冻结口径。

### 8.2 MVP 定义（批次 0 · 对齐基线）

1. 补齐 `douyin-creators`、`douyin-request-logs` 两页的原型与 FR 编号（或明确决策下线），解除 §6.5 冻结区
2. 修复已知问题高优先级：#1 服务状态接真实健康检查、#2 超管危险操作、#3 清理 MediaPipelinePanel 死代码、#9 品牌标题统一、#10~13 命名口径统一
3. 本规范 §6.3/§6.4 与实现逐条核对一遍（首次执行即完成文档自证的闭环）

### 8.3 Phase 2（IA 优化三批次，全部纯前端，源自体验评估文档「落地顺序建议」）

| 批次 | 内容 | 改动面 | 验收 |
| --- | --- | --- | --- |
| 1 | 关键词「采集概览」列合并 + 默认排序改最近获取升序 + 操作列/表格列收敛 | `douyin-keywords.tsx`、资源库卡片 | 本规范 §6.5 P1-01/P0-05 验收 + 新列四态（已爬取/进行中/上次失败/从未爬取） |
| 2 | 创建任务关键词选择器 + 300ms 防抖实时查重 + 批量入口闭环（失效 query + toast 跳转链接） | `CreateTaskDialog.tsx`、`CreateKeywordsDialog`、两个批量入口 | 创建路径 3 步无盲区（体验评估 §三） |
| 3 | 统一「开始采集」Stepper 向导 + 四入口归一 + 指标卡收敛与语义色 + 视觉锚点 | 新增向导组件、赛道页减负、各页指标卡 | 向导三步规格 + 每页 ≤4 指标卡 |

### 8.4 每次交付的质量门禁（agent 完成任一页面后必跑）

```bash
cd frontend
npm run lint          # biome
npm run build         # tsc -p tsconfig.build.json && vite build
bunx playwright test   # 涉及交互流程时
```

人工/agent 走查清单：§6.5 该页全部 Given/When/Then → §6.6 三态矩阵 → 浅/深 × 三主题 × 两密度组合 → 移动端 `md` 断点 → §6.7 五条全局约定。

### 8.5 维护协议（三源同步规则）

**变更顺序（强制）**：

1. **功能变更**：先改 `灵感采集台产品需求文档PRD.md` 对应 FR 条目（或新增 FR 编号）→ 再改原型对应 render 函数 → 再改本规范 §6.2/§6.5 映射与验收
2. **纯视觉/交互变更**：改原型 → 改本规范 §6.3/§6.5；产品 PRD 不动
3. **纯文案变更**：改 `前端逆向产品能力文档.md` → 原型同步 → 本规范不动（除非涉及验收标准中的文案断言）
4. **新增页面**：必须先产出原型 render 函数并更新 §6.2 总表，agent 才可开发——无设计源的页面一律按冻结区处理

**同步检查清单**（每次 PR 自查）：

- [ ] 涉及页面在 §6.2 的「设计源状态」仍为 ✅
- [ ] §6.5 该页验收标准与实现一致（改动若使某条 AC 失效，须先更新 AC 再合并）
- [ ] 文案 diff 中的每一行都能追溯到逆向能力文档或产品 PRD
- [ ] 本文档「修订记录」表新增一行（版本 + 日期 + 说明）
- [ ] 若改了轮询/数据行为，产品 PRD §7.2 轮询表同步

**基线锚点**：每版本文档记录代码基线（分支 + 提交哈希）；agent 接手时若发现当前 HEAD 与基线差异过大，应先要求维护者更新本文档再开发。
